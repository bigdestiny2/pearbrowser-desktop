What PearBrowser becomes

A simple tour of the P2P browser once naming, cryptographic publishing, public mirrors, and trust panels are fully in place. Think of it as: a normal browser UX for sites and apps that live on Pear, with optional bridges to ENS and IPFS — and without handing your keys to a server.

Pear Deploy is not a separate product window you bolt on later. In this map it ships as a Pear Plugin inside PearBrowser — the publish / preview / promote console — while portable pear.deploy contracts stay inspectable and usable from CI or CLI.

1. The big picture

PearBrowser is a desktop (and later mobile) browser for the peer-to-peer web. Instead of “type a DNS name → trust a company server,” you open content addressed by cryptographic keys, signed releases, and optional public names — while your device verifies what it got.

Classic browser

  • DNS names point at servers
  • HTTPS proves the server, not the app author forever
  • Apps = download installers / app stores
  • When the host is gone, the site is gone

PearBrowser (full capability)

  • Keys, petnames, ENS, and CIDs as entry points
  • Signatures + content addresses prove exact bytes
  • Apps launch from catalogues; updates are content
  • Relays keep bytes available after the publisher leaves

Simple rule: publishers sign meaning, content addresses prove integrity, relays provide availability, PearBrowser verifies, and each app decides its own trust/merge policy.

7. Pear Deploy as a Pear Plugin

On this map, Pear Deploy is integrated into PearBrowser as a first-class Pear Plugin — not a separate SaaS dashboard and not a mandatory second app you install to ship. The browser already has a Plugins model (capability-declared Hyperdrives, install by key, re-approval on capability escalation). Deploy rides that same rail.

What the plugin is for

  • Human-friendly publish / preview / promote UX
  • Review exact artifacts, providers, costs, and limitations
  • Hand release digests to external project signers
  • Show native channel + name/mirror convergence status
  • Prepare ENS intents for an external wallet
  • Export CAR + signed mirror manifest

What it deliberately is not

  • Not the only way to build or sign a release (CLI/CI still valid)
  • Not a mandatory hosted controller
  • Not the source of app truth or merge policy
  • Not allowed to escalate capabilities silently
  • Not a place that stores ENS or release seed phrases
  • Not a free pass for pages to pin or deploy

9. Human names that stay honest

Memorable names are great. Lying about them is not. PearBrowser is petname-first: your aliases beat everything, and every resolution keeps a provenance label.

  • Homograph warnings for lookalike characters
  • Conflicts shown, not auto-picked by relay order
  • High-water marks prevent silent version rollback
  • Offline petnames still work with no network

11. Content Shield & plugins

Content Shield

  • Brave-style ad/tracker blocking inside the browser-owned proxy
  • Blocked requests never reach peers or relays
  • P2P filter lists sync as Hyperdrives with sha256 verification
  • Works offline once lists are local

Pear Plugins (including Deploy)

  • Extensions as Hyperdrives with declared capabilities
  • Install by key or from plugin catalogue
  • New capability requests auto-disable until re-approved
  • Hash-authorized injections only
  • Pear Deploy is the publisher-facing core plugin on this model

How to read this document: wireframes are teaching pictures, not product commitments or final visual design. Version numbers and gates live in the engineering roadmaps. PearBrowser remains an independent verifier — not a wallet custodian and not the source of application truth. The Deploy plugin is orchestration UX; portable proofs must still verify without trusting the plugin’s local database.
